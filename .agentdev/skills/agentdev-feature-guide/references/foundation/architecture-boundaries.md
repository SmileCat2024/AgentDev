## 选择 Feature 边界

一个 Feature 应围绕一个稳定的用户目标组织。以下信号说明内容属于同一 Feature：

- 工具共享相同权限、客户端或配置；
- 工具操作同一类领域对象；
- hooks 只服务于这些工具的工作流；
- 状态可以用一个领域模型解释；
- 删除其中一部分后，剩余能力仍有清晰名称。

以下信号说明应拆分：

- 不同工具使用不同凭据和故障域；
- 某组工具可以独立安装、禁用或替换；
- 一个 Feature 同时拥有无关的文件、消息、日历等领域；
- 状态字段之间没有共同不变量；
- 权限策略必须分别审查。

## 选择工具或 Hook

使用工具表达 Agent 可主动选择的动作。使用 hook 表达框架边界上的确定性策略。

| 问题 | 选择 |
|---|---|
| Agent 是否应决定何时执行 | 工具 |
| 每次写操作都必须经过的校验 | ToolUse guard |
| 工具完成后必做的审计 | ToolFinished 钩子 |
| 每轮需要条件提醒 | StepStart 钩子 |
| 无工具调用时仍需继续 | StepFinish guard |
| 只在初始化执行一次 | `onInitiate()` |

不要把本应确定执行的安全校验写成可选工具。不要用 hook 偷偷执行 Agent 应知晓的大型外部副作用。

## 划分内部模块

常用模块：

- `index.ts`：Feature 装配和公开导出；
- `types.ts`：配置、状态、公开 API 和领域类型；
- `config.ts`：manifest 与运行时解析；
- `service.ts`：领域操作；
- `client.ts`：SDK、协议或进程适配；
- `tools/*.ts`：工具契约与工厂；
- `hooks.ts`：规则组合或状态机；
- `state.ts`：快照归一化与迁移；
- `templates/`：纯展示模板；
- `skills/`：跨工具工作流知识；
- `test/`：契约和集成测试。

小 Feature 可以合并文件，但仍保持这些职责在代码结构上可区分。

## 状态所有权

每个可变值必须只有一个明确所有者：

- 领域状态由 Feature 或领域服务拥有；
- 工具通过方法访问，不直接修改集合；
- hook 调用同一领域方法，不维护第二份状态；
- Context 只保存对话消息，不作为业务数据库；
- 外部系统是真实来源时，Feature 缓存必须有刷新规则。

跨 Feature 状态通过公开 API 读取。返回副本或只读视图，禁止返回内部 `Map`、数组、客户端和控制器。

## 依赖方向

允许：

```text
Feature A → Feature B 的公开 API
工具 → 本 Feature 的领域服务
hook → 本 Feature 的状态机
模板 → 工具结果结构
```

避免：

```text
领域服务 → Agent
Feature A → Feature B 私有字段
模板 → 网络或文件系统
restoreState → 创建客户端
工具 → 修改另一个 Feature 的内部集合
```

循环依赖通常意味着边界不清。提取一个更小的公共能力，或让 Agent 装配层负责协调。

## 边界审查

- Feature 名称能否概括全部工具和状态？
- 每个工具是否都属于同一权限域？
- 是否存在只为某一个工具服务却很重的独立资源？
- 是否能单独禁用某一组能力而不破坏其他能力？
- hook 是否只影响本 Feature 负责的行为？
- 公开 API 是否小于内部实现面？
- 是否有隐式全局变量或单例形成第二个状态源？
- 故障是否能限制在本 Feature 内？
