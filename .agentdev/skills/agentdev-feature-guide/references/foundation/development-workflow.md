## 定义交付目标

先写一份不超过一页的 Feature 设计说明，至少回答：

- Feature 解决哪个领域问题；
- Agent 能完成哪些用户目标；
- 哪些行为明确不属于该 Feature；
- 是否读写外部系统；
- 是否需要长期连接、后台任务或子进程；
- 哪些状态需要随 checkpoint 和 session 恢复；
- 是否依赖其他 Feature；
- 失败时应阻止、降级还是允许继续。

用可验证句式描述目标：

```text
提供记录查询和更新能力；查询可并发，更新串行；
更新只能作用于配置的工作区；连接失败时查询工具返回明确不可用错误；
最近访问记录随会话恢复，客户端连接不进入快照。
```

不要用“接入某 SDK”“封装某 API”代替能力目标。SDK 是实现手段，不是 Feature 边界。

## 建立能力清单

逐项决定是否需要：

| 能力 | 产物 |
|---|---|
| Agent 主动调用 | `Tool[]` |
| 远端发现 | `getAsyncTools(ctx)` |
| 工具共享运行时对象 | `getContextInjectors()` 或闭包 |
| 初始化和清理 | `onInitiate()` / `onDestroy()` |
| 输入或 step 行为 | Feature hooks |
| 人类可编辑设置 | manifest + 配置解析器 |
| 回滚和会话恢复 | capture/restore |
| Feature 间协作 | 小型公开 TypeScript 接口 |
| 查看器展示 | `Tool.render` + 模板 |
| 多工具使用知识 | Feature 自带 skill |

删除没有明确使用场景的能力。空 `getAsyncTools()` 和无意义模板只会扩大维护面。

## 设计契约

按以下顺序固定契约：

1. Feature 名称和一句话描述；
2. 工具名称、调用条件、参数和结果；
3. 构造参数与 `featureConfig` 优先级；
4. 公开 API 与依赖名称；
5. 逻辑状态、缓存和运行时资源；
6. hook 的触发条件与退出条件；
7. 错误分类、降级模式和安全策略；
8. 模板与 skills 交付方式。

在写实现前为每个工具列出：

```text
前置条件 → 参数校验 → 外部副作用 → 成功结果 → 可修正失败 → 不可恢复失败
```

## 实现顺序

推荐顺序：

1. 定义领域类型和纯配置解析函数；
2. 实现领域服务与外部适配器；
3. 实现公开 API；
4. 实现工具工厂和 schema；
5. 实现 Feature 装配；
6. 加入生命周期和资源清理；
7. 加入 hooks 和状态机；
8. 加入快照恢复；
9. 加入渲染模板与 Feature skills；
10. 加入集成测试和构建产物验证。

保持依赖方向：

```text
Feature 装配 → 工具工厂 → 领域服务 → 外部适配器
             → hooks/state
```

领域服务不要反向依赖 Agent 或 Context。

## 验证顺序

每完成一层立即验证：

1. 纯函数：配置、路径、迁移、名称映射；
2. 工具契约：schema、描述、结果、错误；
3. Feature 单元：工具集合、上下文注入、公开 API；
4. 生命周期：初始化、部分失败、重复销毁；
5. 状态：capture/restore 往返与非法输入；
6. hook：每个决策出口和短路顺序；
7. Agent 集成：真实注册、工具批次、Context 写入；
8. 构建产物：入口、声明、模板、skills 和资源；
9. 最小消费：从打包结果安装并执行一次完整 call。

## 完成标准

- 一句话边界与实际工具集合一致。
- 每项外部副作用都有校验、幂等或补偿策略。
- 每个后台资源都有所有者、停止信号和等待清理路径。
- 初始化失败不会让工具以半初始化状态执行。
- 配置声明、默认值和解析结果一致。
- 快照只含纯数据并能完整恢复行为。
- hook 有退出条件，异常策略明确。
- 动态挂载、禁用、移除的支持范围明确并经过测试。
- 日志能定位 Feature、工具、hook 和失败阶段。
- 构建产物能被一个空白消费项目直接使用。
